# 技术说明：Homeworld Remastered 的纹理内存预算与"计数器下移"方案

> 本文记录 `se9ccn_texture_budget` 的依据：地址、判断语义、实测数据，以及为什么最终选
> "启动时把计数器一次性下移 32 GiB"。证据来自对 `HomeworldRM.exe`（2.303 / build 3409635）
> 的反汇编、资产普查与运行期观测。

## 1. 引擎里的纹理内存记账与闸门

纹理上传的唯一入口：`FUN_007B4C80`（RVA `0x3B4C80`，`__thiscall`）。反编译关键片段：

```c
uVar3 = (bpp * (fmt + 3) * w * h) / 6;      // 本张纹理的估算字节数
*(uint*)(tex + 0x18) = uVar3;               // 单张纹理记账
delta = uVar3 - old;
DAT_009aed28 += delta;                      // 64 位全局计数器（低 dword @0x9AED28，高 @0x9AED2C）
if (DAT_009aed2c >= 0 && (DAT_009aed2c != 0 || 0x77770000 <= DAT_009aed28)) {
    return 0;                               // 超预算：纹理创建失败（静默）
}
... glTexImage2D ...
```

对应机器码（文件偏移 `0x3B40F3` = RVA `0x3B4CF3`）：

```
78 13                    js   short ok        ; 高 dword 为负 → 直接放行
7F 08                    jg   short fail      ; 高 dword 为正（总量 ≥ 4GiB）→ 直接失败
81 FF 00 00 77 77        cmp  edi, 077770000h ; 低 dword 与阈值做【无符号】比较
72 09                    jb   short ok        ; 小于阈值 → 放行
                         ; 落空 → 失败（返回 0）
```

**判断语义（重要）**：设 T 为计数器的 64 位补码值，

| T 的范围 | 结果 |
|---|---|
| T < 0（最高位为 1） | **放行**（"还剩很多空间"） |
| 0 ≤ T < 4 GiB | 低 32 位无符号比较：T < `0x77770000` 放行，否则拒绝 |
| 4 GiB ≤ T < 2⁶³ | 拒绝（`JG`） |
| T ≥ 2⁶³ | 放行（高位为负，`JS`） |

也就是说，**只有 `T ∈ [0x77770000, 2⁶³)` 这个窗口会拒绝创建纹理**；一旦计数器变成负数，
闸门就无条件放行。这一点是本工具方案的基础。

`0x77770000` = 2,002,796,544 字节 ≈ **1.867 GiB**；全镜像里该立即数只出现一次。
计数器的所有更新都是"加减 delta"（每张纹理创建 +size、销毁 −size），因此**整体平移不破坏记账**。

## 2. 为什么 4 个种族就吃满、8 个种族必炸

- 资产普查（`.big` 解包 + HOD 内嵌贴图描述符反算）：4 个可选种族的船贴图合计
  **1903.9 MB = 该预算的 99.2%**；
- 8 个不同种族的运行期实测：计数器峰值 **2,004,963,872 字节（100.03% 预算）**，
  同时 `Unable to retrieve UI` 出现 2,422 条；若先失败的恰好是必需 UI 贴图，
  `UIGraphic::parseLODTextures`（RVA `0x2B8FF5`）会直接 `-- FATAL EXIT --`，原文
  `Unable to load texture (data:UI\Pings\Meshes\Circle.mtga)`。

## 3. 方案演进与最终选择

| 版本/方案 | 做法 | 结果 |
|---|---|---|
| v1.1 / v1.2 | 改闸门里的比较阈值（甚至去掉 4GiB 高位检查） | 只绕过一处判断；Steam 正式安装的 8 种族局**仍 FATAL**（当时计数器 ≈1.6GB） |
| v1.3 | 每 250ms 采样，>1500MiB 就 −512MiB | **8 种族跑通**（首次成功）；但周期性改写存在极小的读写竞争，且需常驻轮询 |
| **v1.4（当前）** | **启动时一次性把计数器整体下移 32 GiB**，2 秒看门狗仅兜底 | 效果等价、更简单：写入发生在任何纹理创建之前（无竞争）；34 GiB 余量足够覆盖任何一局 |

为什么 32 GiB：负偏移后，计数器要净增 ≈34 GiB 的纹理才会重新进入"拒绝区"；
而 8 个不同种族一场约 2.6~5 GB，留足余量。看门狗阈值取 -16 GiB（偏移量的一半），
只有"计数器被重置/异常爬回"时才会再次下移。

其它被否掉的方案：Hook `FUN_007B4C80`（`__thiscall` + 自定义栈清理、热路径，替身出错会污染绘制流程）；
降低贴图分辨率（mod 侧改动）；LAA/4GB 地址空间（实测 8 种族时进程 commit 仅约 1GB，与预算无关）。

## 4. 边界与安全

- 只影响"纹理预算"这一类判断，不改变显存容量：贴图总量超过显存时驱动回退到系统内存，
  表现为变慢/掉帧，而不是丢贴图；
- **不修改磁盘文件**：只改进程内计数器，重启即恢复，Steam 校验无影响；
- 启动时对目标 exe 做 8 字节签名校验（只读），版本不匹配则**不启用任何功能**（失败安全）；
- 计数器写入是"先写高 dword、再写低 dword"，且发生在启动早期（无纹理创建），无竞争；
- 日志每次启动重写，单次上限 256 KB；
- 线程随 DLL 常驻（DLL 已 `GetModuleHandleEx` PIN），正常情况下每 2 秒只做两次 32 位读。

## 5. 验证方法

1. 启动游戏，看 `se9ccn_texture_budget.log` 是否有
   `counter offset applied (startup): 0 MiB -> -32768 MiB` 与 `done:`；
2. 开一局 8 个不同种族的 mod 对局；正常不应再出现 `counter offset applied (watchdog)`；
3. 游戏内 UI 图标不应再出现红黑方块；`HwRM.log` 里不应再出现
   `Unable to retrieve UI (animated) texture` 或 `Unable to load texture`。
